# vwf's skills and agents

The three artifact families under `plugins/vwf/`: the workflow skills, the
subagents they delegate to, and the auto-applying doctrine skills. **Each
SKILL.md and agent file is authoritative for its own behavior** — the tables
here are an index, not a second copy.

- `skills/` (workflow) — the `/vwf:` workflow skills (each
  `skills/<name>/SKILL.md`), implementing the Product → Blueprint → Plan →
  Execute model. Most are slash- **and** model-invocable because **other skills
  delegate to them by name**; five are **user-only**
  (`disable-model-invocation: true`) — `execute`, `mockups`, `recall`, `setup`
  and `verify`; five — `init`, the three import adapters `import-design-system`,
  `import-screens`, `import-conversations`, and `plan-management` — are
  **skill-invoked**, `user-invocable: false` beside
  `disable-model-invocation: false` and no `paths:`, so each is hidden from the
  `/` menu and reached only by the skill that owns its seam (`/vwf:setup`,
  `/vwf:design-system`, `/vwf:screens import`, `/vwf:feedback canvas`, and the
  two planners plus `execute` — or a session, when the user asks in prose to
  archive a folder or list the queue — respectively) — see Invocation policy
  below. **Each SKILL.md is the authoritative description of its own behavior**;
  the table below is an index, not a second copy — the previous prose version of
  it drifted twice in a single session before being cut.

  | `init`               | Shapes the **base repo and every member repo**, not vwf: the config layout, the toolchain manager's file split and task library, the gates, the hygiene files, a secrets provider, a licence, a two-line readme stub — all of it per repo, each with its own lockfile. **Walks the members**: base per the membership asset (a run started inside a member shapes the product), members the **union** of `.gitmodules` walked recursively and the config's `members:` list deduped on realpath, a path in only one of two present sources reported as a disagreement and never shaped, an absent member given a **clone row inside the same plan**. Mode **new** or **existing**, detected **per repo** on that repo's own markers — no flags, no arguments (one survey → **one plan with a section per repo** → one consent → apply, members first so the base commits its gitlinks current). Asks **seven** questions, one round each for the whole product with a row per repo where the answer differs: the first names each mode-new repo's **folder** — the basename of its main checkout — which is the one thing that fills `REPO_NAME`, slugified and written literally, a member naming its own folder; the second confirms every project id, its slug and the source the name came from — the registry, a sub-project directory, or the project's **platform token**, with `<token>-<directory-slug>` where two projects in one repo pick the same token — grouped by repo, before a single `p:<slug>:*` group, its alias or a commit scope is written, the scopes filled on **every** run including the first, one per confirmed id; the fifth asks which agent plugins the product requires — a multi-select seeded by the plugin task's own inventory mode, written into that task's two marked positions. The aggregator's **member flags and `setup-<slug>` aliases come from the member repos, never from a project id**. The existing-repo pipeline is **eleven** passes **per repo** and **adopts rather than flattens**: an unmapped helper function moves verbatim into the repo-owned `_scripts/local` sidecar (no pack declares it — the one such file `init` writes) instead of being deferred, a task file no pack ships is kept and listed with a contract note where it sits in `setup/` or `code/`, and a pack-owned file whose **content** diverged is **offered** replace-or-keep in the same single plan — divergence being **two tests**, the lock hash and then a splice of every marked position's current value into the pack's payload at the pinned version, so a file differing only inside those positions raises no pass-6 row and only the owning pass's row (e.g. `repo-name key: <old> → <new>`), with a `generated` record skipping the second test. Replace re-fills its marked positions; keep covers the content alone and never a position's value, which the fill passes write either way, and is recorded under `enforcement.kept_files` in the **base's** `.config/vwf.yaml`, a member's keep keyed by its base-relative path (the one key `init` writes into that file, and it never creates it). Materializes the three unconditional bundles by fixed slug, merges the `pre-commit.d/` and `vscode.d/` fragments, and closes with a **consent-gated git pass** whose two questions are asked once for the run — the landing-model question written to `MERGE_MODEL`, stage, one question with three answers (commit / commit and push / leave it), a fixed `ops:` message, the `develop`+`main` pair per repo, and the base staging the moved **gitlinks**. It never touches the forge's own settings; the hygiene pack's `CONTRIBUTING.md` carries that one-time line. Names no tool — every file comes from a pack.   | `setup`              | Phase-0 bootstrapper, and the **one door to `init`**. Takes `[reshape]`, which skips the fork, runs `init` alone and stops — and `reshape` started inside a member reshapes the **product**, since init resolves the base and runs from there. Otherwise a Step-0 **shape check** first, asked of **every repo in the product** (the base and every locally-present member, the same set doctor evaluates): all three unconditional slugs in that repo's adapter lockfile, plus doctor's six baseline predicates on that repo's own artifacts; any missing **or** any failing in **any** repo → one offer of `/vwf:init` naming which repos showed what, a decline is a deferral, an absent member a blind spot. Then Step 0 resolves one of three entry paths — `onboard` (blank repo or repo with code), `migrate` (reconcile the tree against the current format), `current` (report and exit) — then a shared spine validates, stamps `.config/vwf.yaml`, runs `doctor`, commits, and prints the chain forward without running it. It is also where a **pinned** stack is landed: the **materialize pass** (`references/materialize.md`) runs **once per run in every mode**, `current` included — grouping the axes holding a slug the target repo's adapter lockfile does not name, deduping by slug per repo, invoking the adapter once per `(repo, slug)` with the `repo:` line, writing `unresolved` on an **absent** axis and never rewriting a pinned slug. On the spine it runs before the doctor gate; a declined landing leaves the pin and reaches doctor's blocking *pinned, not materialized*   Ordering and what each gate means: **Foundations & ordering** below. The
  execute stage pipeline (`code` → at a `review` row, `review` ‖ `security` →
  `acceptance` + `ux`, the convergence guard, the folder's Run log and its
  journal mirror): `assets/execute-stages.md`.
- `agents/` — the subagents the workflow skills delegate to. Delegation is a
  **latency and context strategy as much as a quality one**: read-heavy scans
  and mechanical writing run in a subagent so their file loads never enter the
  orchestrator's context, where every loaded line is re-processed on each later
  turn. Each agent file states its own contract; `p:plugins:check` verifies
  these names resolve, in both directions.

  There is **no `project-setup` doctrine skill**. Onboarding and migration
  doctrine governs a command run, not a file being edited, so nothing about it
  auto-applies: it lives under `skills/setup/references/` — the topology menu
  and the recognition tables (roles by consumer domain, platforms by evidence)
  in `topology-detection.md`, the target layouts in `workspace-structure.md`,
  the dry-run discipline in `migration-and-consent.md`, and the retired-spelling
  map in `format-lineage.md`. The one structural rule vwf enforces is still
  there: an `iac` project must be its own repo under every topology, which
  `doctor` raises as **blocking** unless a decline is recorded under
  `enforcement:`, after which it is a warning reported every run.
