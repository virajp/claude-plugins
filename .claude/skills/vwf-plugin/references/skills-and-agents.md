# vwf's skills and agents

The three artifact families under `plugins/vwf/`: the workflow skills, the
subagents they delegate to, and the auto-applying doctrine skills. **Each
SKILL.md and agent file is authoritative for its own behavior** — the tables
here are an index, not a second copy.

- `skills/` (workflow) — the `/vwf:` workflow skills (each
  `skills/<name>/SKILL.md`), implementing the Product → Blueprint → Plan →
  Execute model. Most are slash- **and** model-invocable because **other skills
  delegate to them by name**; five are **user-only**
  (`disable-model-invocation: true`) — `execute`, `mockups`, `recall`, `setup`
  and `verify`; five — `init`, the three import adapters `import-design-system`,
  `import-screens`, `import-conversations`, and `plan-management` — are
  **skill-invoked**, `user-invocable: false` beside
  `disable-model-invocation: false` and no `paths:`, so each is hidden from the
  `/` menu and reached only by the skill that owns its seam (`/vwf:setup`,
  `/vwf:design-system`, `/vwf:screens import`, `/vwf:feedback canvas`, and the
  two planners plus `execute` — or a session, when the user asks in prose to
  archive a folder or list the queue — respectively) — see Invocation policy
  below. **Each SKILL.md is the authoritative description of its own behavior**;
  the table below is an index, not a second copy — the previous prose version of
  it drifted twice in a single session before being cut.

After any mode's landing the five new-repo steps run — §3 secrets provider, §4 placeholders, §8 readme/licence/security, §9 bootstrap, §10 aggregator — and, last before the git pass, `init` re-hashes every file it filled, appended to or merged, so nothing it wrote reads as drift.   | `setup`              | Phase-0 bootstrapper, and the **one door to `init`**. Takes `[reshape]`, which skips the fork, runs `init` alone and stops — and `reshape` started inside a member reshapes the **product**, since init resolves the base and runs from there. Otherwise a Step-0 **shape check** first, asked of **every repo in the product** (the base and every locally-present member, the same set doctor evaluates): the `tool-config/<tool>@<version>` records `/stackgen:tool-config all` writes and the one remaining unconditional slug, `repo-hygiene`, in that repo's adapter lockfile, plus doctor's seven baseline predicates on that repo's own artifacts — the seventh, (g), the forge state read through the forge CLI where it answers; any missing **or** any failing in **any** repo → one offer of `/vwf:init` naming which repos showed what, a decline is a deferral, an absent member a blind spot. Then Step 0 resolves one of three entry paths — `onboard` (blank repo or repo with code), `migrate` (reconcile the tree against the current format), `current` (report and exit) — then a shared spine validates, stamps `.config/vwf.yaml`, runs `doctor`, commits, and prints the chain forward without running it. It is also where a **pinned** stack is landed: the **materialize pass** (`references/materialize.md`) runs **once per run in every mode**, `current` included — grouping the axes holding a slug the target repo's adapter lockfile does not name, deduping by slug per repo, invoking the adapter once per `(repo, slug)` with the `repo:` line, writing `unresolved` on an **absent** axis and never rewriting a pinned slug — then **asks the machine env** a landed pack declares (`machine_env:`, each value's `detect` run only while the template entry matches its lockfile hash and offered as the default, handed to `/stackgen:tool-config <tool> set env <name>=<value> for <pack>` as bare data — previewed first, the skill's rows relayed inside setup's question and answered back as `answers=<id>:<answer>` — every previewed row answered, plan rows `ok`, a call missing any row refused whole — a value also set outside the pack's block a **conflict row**, `move-in` or `keep-both` (`keep-existing` for `keep-both` when the line sits in the pack's own file), setup removing no line itself — which writes it in the pack's own block and records the lockfile itself, and committed; `init` never asks these) and **re-runs every already-landed pack's `tool-config:` list** through the skill, the same preview-then-run, so a call a newer pack changed reaches the repo as a drift or conflict row and an unchanged call writes nothing. On the spine it runs before the doctor gate; a declined landing leaves the pin and reaches doctor's blocking *pinned, not materialized*. The pass closes with a **second shape check** — Step 0's two questions over the same repos, against the lockfile the pass just wrote, so a pack version the run moved is offered in the run — once per invocation, the same offer on drift, nothing on clean, and never on `reshape`, which runs no pass   Ordering and what each gate means: **Foundations & ordering** below. The
  execute stage pipeline (`code` → at a `review` row, `review` ‖ `security` →
  `acceptance` + `ux`, the convergence guard, the folder's Run log and its
  journal mirror): `assets/execute-stages.md`.
- `agents/` — the subagents the workflow skills delegate to. Delegation is a
  **latency and context strategy as much as a quality one**: read-heavy scans

  orchestrator's context, where every loaded line is re-processed on each later
  turn. Each agent file states its own contract; `p:plugins:check` verifies
