# vwf's skills and agents

The three artifact families under `plugins/vwf/`: the workflow skills, the
subagents they delegate to, and the auto-applying doctrine skills. **Each
SKILL.md and agent file is authoritative for its own behavior** — the tables
here are an index, not a second copy.

- `skills/` (workflow) — the `/vwf:` workflow skills (each
  `skills/<name>/SKILL.md`), implementing the Product → Blueprint → Plan →
  Execute model. Most are slash- **and** model-invocable because **other skills
  delegate to them by name**; five are **user-only**
  (`disable-model-invocation: true`) — `execute`, `mockups`, `recall`, `setup`
  and `verify`; five — `init`, the three import adapters `import-design-system`,
  `import-screens`, `import-conversations`, and `plan-management` — are
  **skill-invoked**, `user-invocable: false` beside
  `disable-model-invocation: false` and no `paths:`, so each is hidden from the
  `/` menu and reached only by the skill that owns its seam (`/vwf:setup`,
  `/vwf:design-system`, `/vwf:screens import`, `/vwf:feedback canvas`, and the
  two planners plus `execute` — or a session, when the user asks in prose to
  archive a folder or list the queue — respectively) — see Invocation policy
  below. **Each SKILL.md is the authoritative description of its own behavior**;
  the table below is an index, not a second copy — the previous prose version of
  it drifted twice in a single session before being cut.

  | `init`               | Shapes the **base repo and every member repo**, not vwf: the config layout, the toolchain manager's file split and task library, the gates, the hygiene files, a secrets provider, a licence where the repo is public, a two-line readme stub — all of it per repo, each with its own lockfile. **Walks the members**: base per the membership asset (a run started inside a member shapes the product), members the **union** of `.gitmodules` walked recursively and the config's `members:` list deduped on realpath, a path in only one of two present sources reported as a disagreement and never shaped, an absent member given a **clone row inside the same plan**. Mode **`shaped`** (`.config/stackgen.yaml` with `format: 1`), **shaped on the old layout** (no `stackgen.yaml`, but `conf.d/tools.toml`, `conf.d/env.toml` or a root `.config/mise.dev.toml` — named, and the run **stops before the plan** until the old-layout reshape ships), **`source`** (none of those, but a language manifest, a source directory, a root tool config or a `.config/`) or **`blank`** (none of those), detected **per repo** from that repo's own tree — no flags, no arguments, setup's fork never handed down; `source` runs the new-repo landing plus the survey passes with something to read. A **stack read** — in `source` mode only, a fixed manifest table (`package.json`→node, `pyproject.toml`/`requirements.txt`→python, `pubspec.yaml`→dart, `go.mod`→go, `Cargo.toml`→rust, `Package.swift` or a root `*.xcodeproj` directory→swift) — drives one thing, the sub-project proposals; the ignore set is a universal superset, so no template is asked for (one survey → **one plan with a section per repo** → one consent → apply, members first so the base commits its gitlinks current). Asks **five** questions in **six** rounds, one round each for the whole product with a row per repo where the answer differs: the first names each `blank` or `source` repo's **folder** — the basename of its main checkout — which is the one thing that fills `REPO_NAME` — passed as `--repo-name` and stored as `repo_name` in `.config/stackgen.yaml` — slugified and written literally, a member naming its own folder; the second confirms every project id, its slug and the source the name came from — the registry, a sub-project directory, or the project's **platform token**, with `<token>-<directory-slug>` where two projects in one repo pick the same token — grouped by repo, before a single `p:<slug>:*` group, its alias or a commit scope is written, the scopes filled on **every** run including the first, one per confirmed id; the fifth asks each repo's **visibility**, `public` or `private`, defaulted from the forge where the repo's origin can be read and `private` otherwise, recorded nowhere in the tree, and its two dependent parts are the **sixth round**: 5a the licence (MIT / Apache-2.0 / none), a row per `public` repo only — a private repo gets no `LICENSE`, an existing licence file — `LICENSE`, `LICENSE.md`, `LICENCE` or `COPYING` — is kept whatever the answer — and 5b the security contact, a public repo's row defaulted to its origin's advisories page, a private repo's a free email or internal URL with no default, either spliced into the hygiene assets' security template's one contact slot (the issue chooser's *Report a vulnerability* link takes a URL contact and is removed for an email or a decline), a decline writing no file. The forge read from each repo's `origin` host and the provider slug question 4 picked make the `answers:` map the secrets provider's fetch passes the materializer beside `repo:`, keyed `forge` and `secrets`, both always present, `none` the **no-match** value (no `when:` names it, so a conditioned file is skipped: a repo with no remote gets no forge files until the reshape after the remote); a pack's `conditional:` files are evaluated against them, a skipped path listed in the plan under a per-repo **Skipped** heading (`<path> — <pack>, <axis>: <value or none>`, not a conflict, not a keep, not a deferral) and recorded in the lockfile's `skipped:` list; the same two are **recorded** in each repo's `.config/stackgen.yaml` by the `all` call (`--forge`, `--secrets`), which `/vwf:setup`'s materialize pass and `/stackgen:stackgen-sync` read, each re-reading `forge` live from `origin` and re-passing it through `all --forge` where the held value is stale. The aggregator's **member flags and `setup-<slug>` aliases come from the member repos, never from a project id**. **switch** runs `setup:precommit --force` as the last shaping step), the rename map never a task-file basename and never an entry `.gitignore` ignores, a directory holding a project listed once under **Projects**; `.gitignore`, `.gitattributes` and `.graphifyignore` are handed to the skill's git and graphify tools, never offered — a file with no marker pair is one `write` row replacing it whole, so init lists the repo's **own lines** under it and appends them below the closing marker on `ok`, and `.gitattributes`, which has no markers, gets its own lines appended to the end with every later preview preselecting `keep-existing`; passes 3/4/9 read inline `[tasks.*]` tables as tasks; pass 2 rewrites the readme's callers; an unmapped commit type is the skill's pre-commit conflict row — and the replace-or-keep offer runs in **every** mode, over every path the materializer reports as a conflict, a readme, licence or security file already there kept outright: an unmapped helper function moves verbatim into the repo-owned `_scripts/local` sidecar (no pack declares it — the one such file `init` writes) instead of being deferred, a task no pack ships — a file or an inline table — is kept and listed with a contract note where it sits in `setup/` or `code/`, and a pack-owned file whose **content** diverged is **offered** replace-or-keep in the same single plan — divergence being the lock hash, or the pack's bytes where the lockfile has no record; a file `/stackgen:tool-config` renders, and a `rendered: true` pack template, is never offered, its preview showing it as a row. Keep covers the content and is recorded under `enforcement.kept_files` in the **base's** `.config/vwf.yaml`, a member's keep keyed by its base-relative path (the one key `init` writes into that file — into a **stub** of `config_format` plus `enforcement` where the file does not exist yet, so nothing is deferred); replace and keep both **re-record the file's hash** in the lockfile. After any mode's landing the four new-repo steps run — §3 secrets provider, §4 placeholders, §8 readme/licence/security, §9 bootstrap (the executable bit; trust is the user's prerequisite, which the survey checks before the plan and `init` never grants) — and, last before the git pass, `init` re-hashes every pack file it replaced or kept, so nothing it decided reads as drift. a member the run clones is checked out on the remote branch holding the recorded gitlink commit, so it never arrives detached), the landing-model question **one row per repo per branch** passed to `all` as `--merge-model-develop` and `--merge-model-main`, stored as `merge_model` in `stackgen.yaml` and rendered into `MERGE_MODEL_DEVELOP` and `MERGE_MODEL_MAIN`, the `develop`+`main` pair per repo — created beside a mainline of another name, `master` or `trunk`, which is left in place and reported — `develop` checked out, stage, one question with three answers (commit / commit and push / leave it), a fixed `ops:` message **on `develop` in every mode**, the push, and the base staging the moved **gitlinks** — then the **forge pass**, once for the product after the last push, on one further consent: for each repo whose answer was *commit and push*, the default branch on the forge (`develop` preselected, `main` the other) and protection on `develop` and `main` — no force-push, no deletion, a pull request required on each branch whose own value is `pr` — `merge_model.develop` for `develop`, `merge_model.main` for `main`; GitHub through one ruleset per branch named `vwf-<branch>`, GitLab through `protected_branches`; a branch already protected in any form left exactly as it is and reported — and, base only, last, the backlog skill's missing-project procedure invoked by name (never the project-creating command). Those three are the only forge settings it touches; a repo not pushed reads `pending`, and a precondition miss (no CLI for the forge, not logged in, a refused call) or a declined consent prints the by-hand list — the form the hygiene assets' `CONTRIBUTING.md` keeps — and continues. Names no tool, and fetches no bundle — every file comes from a pack, the skill or its own assets. Re-runnable by doctrine, not once — and four commands bring the user to the door, each **offering** `reshape` the Step 0 way and silent when clean: `/vwf:architecture` through setup, `/vwf:setup` after its materialize pass, `/stackgen:stackgen-sync` invoking `/vwf:setup reshape` in-session, `/vwf:recall` printing one drift line from `/vwf:doctor baseline`. **Skill-invoked**: hidden from the `/` menu, reached from setup's Step-0 offer or `/vwf:setup reshape` | no stack-adapter plugin installed → **halt** with the install command; a declined write is a recorded deferral, never a halt; idempotent **for the same id source**, across the product — a second run prints a section per repo each reading nothing; a registry appearing between runs is reported as *id source changed*                                                                                                                                                                           |
  | `setup`              | Phase-0 bootstrapper, and the **one door to `init`**. Takes `[reshape]`, which skips the fork, runs `init` alone and stops — and `reshape` started inside a member reshapes the **product**, since init resolves the base and runs from there. Otherwise a Step-0 **shape check** first, asked of **every repo in the product** (the base and every locally-present member, the same set doctor evaluates): `.config/stackgen.yaml` with `format: 1`, the file `/stackgen:tool-config all` writes — no pack slug is checked; a repo with no `stackgen.yaml` but the old mise layout is **shaped on the old layout**, named, and setup **stops** — plus doctor's seven baseline predicates on that repo's own artifacts — the seventh, (g), the forge state read through the forge CLI where it answers; any missing **or** any failing in **any** repo → one offer of `/vwf:init` naming which repos showed what, a decline is a deferral, an absent member a blind spot. Then Step 0 resolves one of three entry paths — `onboard` (blank repo or repo with code), `migrate` (reconcile the tree against the current format), `current` (report and exit) — then a shared spine validates, stamps `.config/vwf.yaml`, runs `doctor`, commits, and prints the chain forward without running it. It is also where a **pinned** stack is landed: the **materialize pass** (`references/materialize.md`) runs **once per run in every mode**, `current` included — grouping the axes holding a slug the target repo's adapter lockfile does not name, deduping by slug per repo, invoking the adapter once per `(repo, slug)` with the `repo:` line, writing `unresolved` on an **absent** axis and never rewriting a pinned slug — carrying the `answers:` map (the forge and secrets provider that repo's `stackgen.yaml` holds, the forge re-read live) and a `values:` map — pack slug → lowercase name → value — of each pack's `values:` entries, gathered by its `detect` command, else its `question`; the materializer copies `config/`, runs `/stackgen:tool-config pack --slug --dir --set <name>=<value>` for `templates/` (previewed first, its rows relayed inside setup's question and answered back as `--answers <id>:<answer>`) and records each rendered path `rendered: true` with no hash; `init` never asks these. Every run **re-runs `pack` for each already-landed pack**, so a template a newer pack changed reaches the repo as a `write` row and an unchanged pack writes nothing; a dropped pack goes through `pack-remove`, then its recorded files are deleted; and after the packs setup re-derives `node` and `external` and calls `all` with the ones that changed. On the spine it runs before the doctor gate; a declined landing leaves the pin and reaches doctor's blocking *pinned, not materialized*. The pass closes with a **second shape check** — Step 0's two questions over the same repos, against the lockfile the pass just wrote, so a pack version the run moved is offered in the run — once per invocation, the same offer on drift, nothing on clean, and never on `reshape`, which runs no pass   Ordering and what each gate means: **Foundations & ordering** below. The
  execute stage pipeline (`code` → at a `review` row, `review` ‖ `security` →
  `acceptance` + `ux`, the convergence guard, the folder's Run log and its
  journal mirror): `assets/execute-stages.md`.
- `agents/` — the subagents the workflow skills delegate to. Delegation is a
  **latency and context strategy as much as a quality one**: read-heavy scans

  turn. Each agent file states its own contract; `p:plugins:check` verifies

  There is **no `project-setup` doctrine skill**. Onboarding and migration
  doctrine governs a command run, not a file being edited, so nothing about it
  auto-applies: it lives under `skills/setup/references/` — the topology menu
  and the recognition tables (roles by consumer domain, platforms by evidence)
  in `topology-detection.md`, the target layouts in `workspace-structure.md`,
  the dry-run discipline in `migration-and-consent.md`, and the retired-spelling
  map in `format-lineage.md`. The one structural rule vwf enforces is still
  there: an `iac` project must be its own repo under every topology, which
  `doctor` raises as **blocking** unless a decline is recorded under
  `enforcement:`, after which it is a warning reported every run.
