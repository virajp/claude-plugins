All three carry `unconditional: true`; `/vwf:init` fetches them by fixed slug,
in the materializer's composition order — manager, gates, hygiene — so a later
component's file wins where two write one path
(`plugins/vwf/skills/init/references/new-repo.md:62-68`;
`plugins/stackgen/assets/output-tree.md` §Composition order). The inventory
agrees on every pin (`plugins/stackgen/stacks/inventory.md:152,161,162`). No two
of the six packs write the same `config/` path, so composition order decides
nothing among the baselines today; it decides the overlays a stack lands later
(the pnpm, uv, flutter, ruff and eslint packs overlay `code/format`, `code/lint`
and `setup/deps/*`, and the secrets providers overlay `setup/secrets`).

**What the materializer does with an existing path, in both modes.** The only
collision check is against the target repo's own `.claude/stackgen/lock.yaml`: a
path that exists and is not recorded there is *"a conflict listed for the user
to resolve, never a write"*
(`plugins/stackgen/skills/stackgen-stack-template/references/materializer.md:167-179`;
`plugins/stackgen/assets/output-tree.md:394-396`). In mode **new** there is no
lockfile, so every path the repo already has is such a conflict — and the
new-repo pipeline says nothing about what happens to it afterwards
(`new-repo.md:60-75` covers a declined consent line, not a conflicting path;
`new-repo.md:786-794` says *files replaced* and *files kept* read `none`). In
mode **existing**, pass 6 compares the file against the lockfile hash, or the
pack's bytes where the lockfile has no record, and **offers** it replace-or-keep
(`existing-repo.md:271-293`). The two modes therefore treat the same
pre-existing `.gitignore` differently, and mode is decided by the presence of
`.config/` or the task-library directory alone
(`plugins/vwf/skills/init/SKILL.md:173-184`).

## Findings

Severity: **blocks** a user · **surprises** a user · **cosmetic**.

1. **blocks** — The composed `.vscode/settings.json` and
   `.vscode/extensions.json` carry `//` marker lines (`pack-format.md:130-131`,
   `FS:276-282`), and the shipped `check-json` hook has no `.vscode/` exclude
   (`P/.config/pre-commit-config.yaml:132-135`). Once hooks are wired, the first
   commit that stages either file fails on a file init wrote. On the new-repo
   path that is the first commit after `setup:all`; on the existing-repo path it
   is the shaping commit itself, since the gate config commits first with hooks
   live (`ER:852-881`, `NR:561-569`). This repo carries the fix by hand
   (`.config/pre-commit-config.yaml:195-199`), which is how the gap stayed
   invisible.
2. **blocks** — `code:sec` without `--staged` runs `gitleaks dir .`
   (`M/…/code/sec:58`), which reads gitignored files
   (`G/.config/gitleaks.toml:29-30`); the allowlist names five build trees and
   not `.env` (`:42-49`), which hygiene ignores precisely because it holds real
   values (`H/.gitignore:48-54`). A developer with a populated local `.env`
   fails `code:all` and the merge safety net on a file that is correctly
   uncommitted.
3. **blocks** — `code:git-config` runs under the gate with `--fix`
   (`P/.config/pre-commit-config.yaml:49`, `always_run: true`) and unsets a
   local `user.email` / `user.name` / signing key without asking
   (`M/…/code/git-config:16-27`). A repo that set a work identity locally — the
   ordinary way to separate a work address from a global personal one — has it
   removed at its next commit, and the commit lands under the global identity.
4. **blocks** — `setup:precommit` unsets `core.hooksPath` and installs with
   `--overwrite` (`M/…/setup/precommit:29-30`). A brownfield repo on husky or
   lefthook loses its hook wiring silently; init's survey has no pass that reads
   `core.hooksPath`, `.husky/` or `lefthook.yml` (`ER:38-692`).
5. **surprises** — In mode **new** a pre-existing path is a materializer
   conflict and *never a write* (`MAT:167-179`), and the new-repo pipeline never
   says what becomes of it (`NR:60-75,786-794`). A repo with source but no
   `.config/` — the greenfield-with-source case — keeps its own `.gitignore`,
   `.editorconfig`, `.gitattributes`, `SECURITY.md`, `CONTRIBUTING.md`,
   `renovate.json`, root `dprint.json` and any same-named issue template
   unmerged and unoffered, while the same repo with an empty `.config/`
   directory would have every one of them offered replace-or-keep
   (`ER:271-293`). Mode is the only thing that differs (`SKILL.md:173-184`).
6. **surprises** — Two pack-owned, lockfile-recorded files are rewritten by
   pack-owned tasks outside any marked position: `pre-commit autoupdate` moves
   `rev:` lines in `.config/pre-commit-config.yaml` (`M/…/setup/precommit:19`)
   and `dprint config update` moves plugin URLs in `.config/dprint.json`
   (`M/…/setup/mise:44`). Pass 6's second test splices marked positions only
   (`ER:300-316`), so after one `setup:all` both files read as content drift —
   offered on every reshape and red under doctor (e)
   (`plugins/vwf/skills/doctor/references/stack-checks.md:401-423`).
7. **surprises** — The same drift by init's own hand: the ignore-section append
   (`NR:114-123`) and the hook-fragment merge (`FS:103-128`) change `.gitignore`
   and `.config/pre-commit-config.yaml` after the materializer hashed them
   (`MAT:113-117`), neither is a marked position, and only a *replace*
   re-records a hash (`ER:352-355`). A repo whose stack later lands a section or
   a fragment has both files offered as diverged from then on. Whether the
   materializer or init re-hashes after §5–§6 is unspecified in both.
8. **surprises** — `code:format --fix` is the commit hook, and it runs dprint
   over every file its eight plugins claim — there is deliberately no `includes`
   (`D/…/conventions.md:128-151`) — plus `shfmt -i 2 -ci` over every tracked
   shell file (`M/…/code/format:59-75`). On a brownfield repo with prettier,
   black or 4-space shell, every touched file is reformatted at the first
   commit, and the merge safety net refuses until the whole tree has been
   (`_scripts/merge:39-92`).
9. **surprises** — `editor.defaultFormatter: dprint.dprint` is set editor-wide

10. **surprises** — The hygiene editor baseline carries Node, TS, Dart, Astro

## D2 candidates

What a **config-of-intent** — a file naming what the repo wants, read by init
before anything lands — could describe instead of copying, and what must stay a
byte payload.

**Describable — a declaration would replace or condition the copy:**

- The **hygiene root set** (rows 20–29): visibility, forge, update bot, editor,
  contact and licence are already five of init's seven questions; the files are
  the rendering of the answers. A forge answer would suppress
  `.github/ISSUE_TEMPLATE/*` off GitHub (finding 11); an update-bot answer would
  suppress or relocate `renovate.json` (finding 12); an editor answer would gate
  every `vscode.d/*` fragment and `setup:vscode`.
- The **editor baseline's stack keys** (row 30, finding 10): the Node, TS, Dart,
  Astro and Turbo entries belong in the fragments of the packs that pin those
  stacks; the baseline should keep the editor-wide keys alone.
- The **gate thresholds and exclusions** (rows 11, 12, 15, 16, 17): one declared
  exclusion set rendered into four files (finding 20); the grype threshold and
  the `main`/`develop` names as values, not literals (findings 14, 15).
- The **git-config identity rule** (finding 3): whether local identity is
  forbidden is a repo policy; today it is a hook that deletes.
- **Stack detection for the ignore sections** (row 20): the `stacks:` pin or the
  registry's platform token could drive §5 on a first run instead of a lockfile
  that names nothing (`NR:119-123`).

**Must stay byte payloads:**

- The **task library** (rows 6–10) — `_scripts/*`, `code/*`, `setup/*` — runs as
  shell; the overlay model (a stack pack replaces a slot file whole) is the
  right conditioning and already works. What D2 owes here is the survey of what
  the tasks *do to the repo* on first run (findings 4, 6, 8, 16), not a rewrite.
- The **gate config files** themselves (`dprint.json`, `taplo.toml`,
  `gitleaks.toml`, `grype.yaml`, `pre-commit-config.yaml`,
  `git-conventional-commits.yaml`) — each tool discovers or is pointed at a
  literal file; intent can *fill* them but cannot replace them.
- The **mise split** (rows 1–4) — mise reads the files; the three marked
  positions are already the intent layer.
- **`LICENSE`** texts, **`SECURITY.md`**, the **issue forms** — prose a forge
  renders, once the decision to land them is conditioned.

**Read-before-land, for whichever files stay copies** (finding 5): the new-repo
path needs the same offer pass 6 gives the existing-repo path for a path the
materializer reports as a conflict — or mode detection needs to read more than
the presence of `.config/`.
