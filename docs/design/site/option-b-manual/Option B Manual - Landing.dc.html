Four phases from a vague idea to a reviewed release.

An opinionated Claude Code plugin: Product, Blueprint, Plan, Execute. Asks one question at a time, then builds unattended.

The four phases

Everything up to the blueprint is done in full before planning. Each phase is one slash command, and Claude never merges until you approve.

1

Product/vwf:product

Pin the outcome contract: the problem, the users, measurable goals, and the order to build in. Everything downstream must trace to it.

2

Blueprint/vwf:blueprint

Keep an always-current blueprint of the whole product, organized by flow, with entities as the data contracts under them, closed by a whole-product coherence review.

3

Plan/vwf:plan

Diff the blueprint against the real code for one slice, planning its unbuilt dependencies as their own chained plans first, and write the delta to apply.

4

Execute/vwf:execute

Implement the plan autonomously under strict TDD, with code review, security review, E2E acceptance and UX conformance, behind one final merge gate.

Install

One command registers the marketplace and installs the workflow. stackgen, its one dependency, comes with it. Restart Claude Code afterwards and run /vwf:doctor.

pnpx @virajp.dev/claude-plugins --all # or Claude Code's own two commands, which the wrapper sequences claude plugin marketplace add virajp/claude-plugins claude plugin install vwf@virajp-plugins

Two plugins ship

vwfvwf@virajp-plugins

The workflow. Onboard a repo, pin the outcome contract, model the system, sweep the blueprint to complete coverage, plan one slice as a reviewable diff, execute it unattended behind one merge gate, verify the deploy, and route what production teaches you back to the document that fixes it.

It names no technology at all. No language, no framework, no cloud. That is what lets the second plugin exist.

stackgenstackgen@virajp-plugins

The principles-driven stack materializer. A stack is a composition of components, and each one resolves on its own: a component a shipped pack covers is copied verbatim; an uncovered one is researched, generated against vwf's principles catalog, and gated by a reviewer agent and your explicit consent.

Most of the result is plain files your collaborators get with a git pull. A vwf dependency, so installing the workflow brings it.

Know this before you install

vwf is deliberately heavyweight, and some of what it needs is a real adoption blocker rather than a preference.

It is built for the 1-million-token context window. The orchestrator holds the blueprint, the plan, the registry and each subagent's output at once. On the standard window a real cycle will degrade or overflow.

It runs opus where judgment decides the outcome, and where nobody is watching. An execute cycle runs several opus subagents per step with fix loop-backs, so expect a meaningful token cost per slice. This is not a cheap workflow.

It expects a testable, registry-described project, and five binaries on your PATH: mise, graphify, uv, pnpm and rtk. Nothing checks this at install time. It is opinionated on purpose: one workflow, one set of conventions, sized for a solo developer or a small team.
