# Jetpack Compose — performance & size

## Measure first

- **Measure a release build**, minified, on a real device or a profileable
  build. A debug build runs Compose with extra checks and is not evidence.
- **Layout Inspector's recomposition counts** show which composables recompose
  and which skip. A count that climbs on every scroll frame is the bug.
- **Compose compiler reports** (`reportsDestination` and `metricsDestination`
  in the `composeCompiler { }` block) list each composable's skippability and
  each class's stability — read them before annotating anything.
- **Macrobenchmark** measures startup and scroll jank in a separate
  `:benchmark` module; a performance claim without one is a guess.

## The usual causes

| Symptom                              | Usual cause                                    | Fix                                            |
| ------------------------------------ | ---------------------------------------------- | ---------------------------------------------- |
| A list recomposes every item on scroll | no `key`, or an unstable item type           | stable `key` per item; immutable item models   |
| Whole screen recomposes on scroll    | scroll state read in the composition phase     | read it in a lambda or `derivedStateOf`        |
| A child recomposes though nothing changed | a new lambda or list instance each time    | hoist, `remember`, or produce state only on change |
| Animation drops frames               | the animated value read during composition    | `graphicsLayer` / `Modifier.offset { }` lambda forms |
| Slow first frame                     | heavy work in `Application.onCreate` or the first composable | defer it; App Startup; a baseline profile |

## Baseline profiles

**Ship a baseline profile.** Compose is a library, so its code is interpreted
until the runtime compiles it; a baseline profile, generated by the
Baseline Profile Gradle plugin from a Macrobenchmark journey through startup and
the main screens, lets it be compiled ahead of time on install. Regenerate it
when the main journeys change.

## Lazy lists

- **`key` every item** with a stable id, and give heterogeneous lists a
  `contentType`, so items are reused rather than rebuilt.
- **Never nest a lazy list in a scrollable of the same direction**; use one
  `LazyColumn` with several item blocks.
- **Images are loaded asynchronously and sized**, by the image library the repo
  picks, at the size drawn — never a full-resolution bitmap scaled down.

## App size

- **R8 with resource shrinking** on `release` — see
  [build & variants](build-and-variants.md).
- **The store delivers an Android App Bundle**, which splits by screen density,
  ABI and language; size is measured on the split a device receives.
- **Material icons**: depend on the core icon set only, or copy the few
  extended icons used as vector drawables — `material-icons-extended` is large.
- **Vector drawables and WebP** for images, and fonts downloaded or subset
  rather than bundled whole.
