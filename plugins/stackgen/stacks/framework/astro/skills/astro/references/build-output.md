# Build output

The seam between the project axis and the deploy axis, stated once so a deploy
pack can cite it.

## Build output

**The build writes `./dist`** — Astro's `outDir` default — and a deploy pack
may rely on that path. It is the contract: what a deploy target uploads, and
where it looks for it.

A repo that changes `outDir` has changed that contract and must change its
deploy configuration in the same commit. Nothing detects the mismatch — a
deploy target pointed at a directory that no longer exists uploads an empty
set and reports success — so the honest default is to leave `outDir` alone.
The same heading appears in this component's `conventions.md`, and the two say
the same thing on purpose: a deploy pack may cite either.

`outDir` is resolved relative to the project root, which is the directory
holding `astro.config`. In a monorepo that is the project's own directory, not
the workspace root, so each project's build output is its own `dist/`.

## What lands there, per mode

| Mode   | `dist/` contains                                              |
| ------ | -------------------------------------------------------------- |
| SSG    | HTML, assets, `404.html` — files only                          |
| CSR    | the shell HTML, the catch-all's HTML, assets — files only      |
| Hybrid | the prerendered files **plus** the adapter's server entry      |
| SSR    | the assets and any prerendered routes **plus** the server entry |

**Files only** means the directory is the whole deployment and no process
runs. **Plus a server entry** means the deploy target has two jobs: serve the
files, and run the entry for everything else.

**The server entry's path is the adapter's, not Astro's.** A deploy config
that names the entry — a container's start command, or a Worker's `main` —
names a path the adapter defines and may move between adapter majors. The
Cloudflare adapter is the live case: its entry moved from a built file path to
a unified entrypoint the package exports, so a deploy config written against
an older major names a file that no longer exists after the upgrade. Read the
adapter's own documentation for the current path; this pack pins neither.

## Post-build steps write into `dist/`, never beside it

A search index, a redirects file, a headers file, a sitemap a plugin did not
emit — each is generated after the build and written **into** the output
directory, as a later command in the same build task.

The reason is that the deploy target uploads one directory. A step that writes
its output to a sibling path produces something the deploy never sees, and the
failure is silent: the site deploys, the feature is simply absent.

**Nothing in `dist/` is committed.** It is regenerated by every build and
ignored by version control. A file that must survive a build is a source file
under `public/`, which Astro copies through verbatim.

## Fingerprinting

Astro fingerprints the assets it emits, which is what makes those paths safe
to cache immutably at the edge. The entry HTML is **not** fingerprinted and
must not be cached that way, or a deploy is invisible to every browser that
already holds the old page. Which side of that line a path falls on is the
deploy pack's cache policy to express; this file only states that the line
exists and where the build puts it.
