# Build output

The seam between the project axis and the deploy axis, stated once so a deploy
pack can cite it.

## Build output

**The build writes `./dist`** — Vite's `outDir` default, resolved to the
directory beside `src/` — and a deploy pack may rely on that path. It is
the contract: what a deploy target uploads, and where it looks for it.

A repo that changes `outDir` has changed that contract and must change its
deploy configuration in the same commit. Nothing detects the mismatch — a
deploy target pointed at a directory that no longer exists uploads an empty
set and reports success — so the honest default is to leave `outDir` alone.
The same heading appears in this component's `conventions.md`, and the two say
the same thing on purpose: a deploy pack may cite either.

**`outDir` is relative to `root`**, which is `src` here, so the config
writes it as one level up — the `dist/` beside `src/`, not inside it. Vite
empties an output directory inside the root without asking and, per its
documentation, only warns for one outside it unless `build.emptyOutDir` is
set explicitly; the config sets it, so the directory is emptied on every
build and a deleted page does not linger as a stale file. In a monorepo the
project root is the project's own directory, not the workspace root, so each
project's build output is its own `dist/`.

## What lands there

| Path                   | Is                                                          |
| ---------------------- | ----------------------------------------------------------- |
| every page in `input`  | at its `src/` path, minified, its asset references rewritten |
| `assets/`              | the stylesheets, scripts, images and fonts the pages reference, content-hashed |
| everything in `public/` | copied through at the root, at the same path, untouched      |

**Files only.** There is no server entry in any configuration of this
component; the directory is the whole deployment and no process runs. That
is the property `cloudflare-workers-static` and any other directory-serving
host is built for, and the pairing decides nothing but the trailing-slash
and not-found behaviour, which the pages-and-navigation reference's URL
shape and `404.html` must agree with.

## The copy-only opt-out

A repo that wants its tree served byte-for-byte — no hashing, no
minification, no rewriting of any reference — replaces the build with a
copy: `cp -R src/. dist/ && cp -R public/. dist/`, in its `build` task, and
keeps `vite` for the dev server alone. The tree the browser receives is then
exactly the tree in the repo.

What it gives up, stated so the choice is made with the cost in view:

- **Content-hashed asset names**, and with them immutable caching at the
  edge: every path in `dist/` is now a mutable URL, and the deploy pack's
  cache policy must treat it as one.
- **Minification.**
- **`.ts` scripts** — nothing compiles them, so every script is `.js`.
- **Any stylesheet approach that needs a build plugin.** The stylesheet
  paragraph in this component's `conventions.md` says which: `plain-css`
  needs nothing, `tailwindcss` falls back to its CLI, `stylex` is
  unavailable.
- **Vite's asset-reference rewriting**, so every reference in a page must
  already be the path it is served at — which, with root-absolute links and
  no hashing, it is.

It is a choice a repo makes once, and states in its own conventions. The
default is the Vite build.

## Post-build steps write into `dist/`, never beside it

A search index, a redirects file, a headers file — each is generated after
the build and written **into** the output directory, as a later command in
the same build task.

The reason is that the deploy target uploads one directory. A step that
writes its output to a sibling path produces something the deploy never
sees, and the failure is silent: the site deploys, the feature is simply
absent.

The sitemap is **not** a post-build step here. No build owns page
discovery, so `sitemap.xml` is hand-authored under `public/` and copied
through — the head reference says how it is kept.

**Nothing in `dist/` is committed.** It is regenerated by every build and
ignored by version control. A file that must survive a build is a source
file under `public/`, which the build copies through verbatim.

## Fingerprinting

Under the default build, Vite content-hashes the assets it emits, which is
what makes those paths safe to cache immutably at the edge. The page HTML is
**not** hashed and must not be cached that way, or a deploy is invisible to
every browser that already holds the old page. Which side of that line a
path falls on is the deploy pack's cache policy to express; this file only
states that the line exists, where the build puts it — and that under the
copy-only opt-out there is no line, because nothing is hashed.
